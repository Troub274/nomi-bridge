# Nomi API Room mode (Chat Bridge 0.4.0)

This is the **third conversation mode**, alongside Direct Chat and Group Chat. It uses one ChatGPT browser tab and a persistent Nomi **API room containing exactly one selected Nomi**. The Nomi's ordinary private chat is not involved, so you can run a World Engine / daily-life simulation entirely inside a separate room.

## Setup

1. Load the updated **extension/** folder via `edge://extensions` → Load unpacked. If already installed, click Reload. (A new permission for `https://api.nomi.ai/*` must be granted.)
2. Open the bridge dashboard; set Conversation mode to **Nomi API room — one Nomi, every turn**.
3. Paste a Nomi API key in Settings and click **Save key**. The key is saved in **Edge extension local storage**, not in GitHub, ChatGPT prompts, bridge snapshots, or troubleshooting reports. Access to the extension/browser profile can still expose locally stored keys, so use a trusted profile.
4. Click **Refresh Nomis and rooms**. Choose **one Nomi** and an existing room containing her, or create a new dedicated room (e.g. `WORLD::Gwen`).
5. Select your ChatGPT tab, and press Play. ChatGPT is always the initial speaker in this mode; send an opening prompt there if needed.

## Manage API rooms from the bridge

With API Room mode selected and the world-engine bridge **stopped**, choose one Nomi and its API room:

- **Create room:** enter an optional name and description (maximum 1,000 characters), then create the room. Backchanneling remains **enabled**.
- **Save description:** edit the selected room's note and save. Only the `note` property is sent; the selected Nomi and backchanneling setting are not modified. The bridge checks for an edit made elsewhere before writing.
- **Delete room permanently:** press **Delete room permanently…**, type the room's exact name, and approve a separate final confirmation. A room with an unfinished send/reply checkpoint must be recovered or explicitly abandoned before deletion.
- Deletion removes the **API room and its room history**, not the Nomi herself. A timeout during deletion has an uncertain outcome; **refresh the list** before trying again. No automatic retries of DELETE or PUT requests.

## Optional World Engine live-chat monitoring (preview)

Enable **Monitor Nomi live private chat** in API Room settings and optionally select the Nomi private-chat tab. If the tab is not open yet, the bridge will try to auto-bind it when the URL contains the selected Nomi UUID or matches a previously chosen conversation URL.

- **World messages always go to the API room.** The bridge never writes them to the Nomi's private chat.
- **When the private-chat tab is actively monitored:** `[say room]` posts the world event to the API room and then sends an **immediate internal delivery acknowledgement to GPT**, without requesting a Nomi API-room reply. The acknowledgement identifies itself as a bridge message—not Nomi speaking—and does **not** advance the private-chat listening cursor. GPT can next send `[listening]` to wait for a completed user/Nomi exchange or another `[say room]` event. If private monitoring is already inactive when the world event is posted, the normal API-room reply path is used instead. The inactivity threshold defaults to **5 minutes** (2–60 minutes).
- **When there is no usable live conversation history** (tab closed, not yet connected, no recognized messages): the bridge uses normal API-room reply requests. If the tab closes mid-session, monitoring drops immediately and future world turns get API-room replies.
- **`[say room]`** followed by text delivers that text to the API room with the existing 800-byte chunking and checkpoint rules. Untagged replies are also treated as world-room sends for backward compatibility.
- **`[listening]`** and **`[wait]`** are strictly passive and never send to Nomi or request a room reply. They wait until at least one complete **User → Nomi round trip** has occurred. Then the bridge delivers **all captured live messages since the previous acknowledged listen**, in chronological order—not just the last reply. Additional user messages without an answer remain buffered. `[tail]` and `[history]` are non-destructive lookbacks and do **not** advance the listen cursor. The cursor advances only after GPT's browser editor confirms the catch-up was received. Large catch-ups are delivered in bounded successive batches, each ending with a complete Nomi reply; GPT can send another `[listening]` to retrieve the next batch. The local journal retains the most recent **500** events, so material older than that can no longer be recovered by the bridge. If live monitoring is disabled or idle, `[wait]` stays silent. To advance the world, GPT explicitly sends **`[say room]`** followed by the world event.
- **`[tail]`** returns the last ten locally observed events, **`[history]`** returns the latest retained history page, and **`[history 2]`**, `[history 3]`, etc. retrieve progressively older pages.
- **`[say chat]` is deliberately disabled** in this preview: private-chat access remains read-only.

The extension keeps the latest **500** events in a separate persistent local journal per API room (source: live chat or room, speaker, observation timestamp and up to 6,000 text characters per event). Reopening Edge does not destroy this journal; ChatGPT can request `[tail]` or `[history]` after restarting. The **Clear local history** button erases the local journal while the bridge is stopped; deleting an API room also clears the journal. Neither action removes Nomi's underlying private chat. Local observation timestamps are when messages were seen by the bridge, not guaranteed original send times.

The bridge activity log now identifies actual `/chat/request` attempts separately from observation deliveries. Each attempt appears as `Nomi API /chat/request attempt N`. This makes unintended reply loops auditable without exporting credentials.

**Browser-selector limitation:** live user/Nomi message reading depends on Nomi's current DOM. If the website changes its message CSS classes, the monitor may report zero observed messages and fall back to room replies. This requires a real Edge/Nomi smoke test before relying on unattended monitoring. While no new private-chat messages arrive, `[listening]` can remain idle; the World Engine does not automatically schedule new time-of-day events merely because monitoring is enabled.

## Control-command and recovery fixes (development build)

**Control tags are never Nomi conversation text.** The World Engine may return `[tail]`, `[history]`, `[history 2]`, `[listening]`, or `[wait]` as its entire response, or as one standalone command line after conversational text. An inline mention such as “I checked [tail]” is prose, **not a second command**. When GPT writes a preamble followed by exactly one standalone `[say room]` line, only the world-event body following that line is posted to Nomi. Multiple standalone commands and malformed tags are never sent to Nomi; a rejection produces a local correction notice addressed to GPT, and the bridge stops after three consecutive malformed commands rather than looping. In active live-monitor mode, a successful `[say room]` immediately returns a **bridge delivery acknowledgement**, NOT a Nomi reply, leaving the private-chat listening cursor unchanged. The dashboard and copied status display build marker `one-shot-listen-r7` alongside 0.4.2.

**Live monitoring never replays stale observations as new Nomi replies.** After a successfully posted `[say room]` event in active live-monitor mode, the bridge immediately returns a **delivery-confirmed notice** to GPT, and completes that event's local checkpoint only after GPT's browser has confirmed receiving the notice. GPT can issue `[listening]` next. That command waits for a **complete User → Nomi exchange**, then delivers all observed private-chat messages since the previous acknowledged listen. Switching through the room never consumes the listening cursor or discards buffered live messages. If monitoring was inactive when the event was sent, an API-room Nomi reply is requested normally. `[wait]` stays passive even across long periods of silence.

**Strict one-shot listening (build `one-shot-listen-r7`):** Each explicit `[listening]` command waits for one completed **User → Nomi** round trip and returns the entire retained new conversation since the last acknowledged listen (subject to bounded message packets). It never remains armed after that response. If no complete exchange appears within 12 seconds, the bridge returns one clear internal timeout status, leaves all observations queued, and awaits another explicit GPT command. A room-only fallback status likewise completes the single request. `[tail]` and `[history]` do not move the listening cursor. The bridge only advances the cursor after ChatGPT confirms the delivered observation, and `pendingReply` resets from `observation_delivering` to `none` on acknowledgement. The copied troubleshooting status exposes `apiRoom.listenRequestPending`, the last acknowledged event number, the pending delivery event number, and the selected ChatGPT tab ID to distinguish an unanswered listen from GPT failing to produce another command. No automatic catch-up is sent without a new `[listening]`. Note: the DOM monitor sees a maximum of **50 recent private-chat messages** at a time, so a restart cannot reconstruct older messages that weren't previously journaled.

**Automatic room-only fallback:** If the private-chat monitor is disabled, its tab disconnects, or it has no new activity within the configured idle threshold, the World Engine **keeps Play running** and switches the effective response path to Nomi's API room. The next `[say room]` message is posted once, then the bridge requests its Nomi API-room reply normally. It does not require another manual Play or change the chosen room. A `[listening]` check with no completed backlog immediately reports `ROOM-ONLY FALLBACK ACTIVE` to GPT; it does not call Nomi or advance the private-chat cursor. `[wait]` stays completely passive. When a usable private-chat tab and fresh messages return, the bridge automatically resumes live monitoring and future room events receive delivery acknowledgements instead of forced room replies. The dashboard reports the effective mode, and **Copy troubleshooting status** includes `apiRoom.effectiveMode` (`live` or `room-only`). This mode switch never reposts a completed world event.

**Listening and unattended Play:** When live monitoring is available, `[listening]` checks for a complete new User → Nomi round trip and, if none arrives within **12 seconds**, returns a bridge-only status to GPT without advancing the listening cursor. `[wait]` remains an indefinite passive wait. In API Room mode, the generic 15-minute no-reply watchdog does not stop Play, and a temporarily disconnected or sleeping tab suspends processing rather than ending the session. An unclaimed send command is dropped on disconnect to avoid acting on stale GPT output. A claimed/uncertain send, tab closure, or repeated protocol errors still stops Play for safety. The Activity log's last stop entry explains the specific cause.

**Late Nomi reply after a GPT navigation (build `late-reply-recovery-r10`):** A selected ChatGPT tab may navigate to a different conversation while `/rooms/{id}/chat/request` is pending. The bridge stops in `uncertain` to avoid delivering the reply to the wrong conversation, but **allows the in-flight Nomi request to finish**. If Nomi replies, the content is durably committed under checkpoint status `reply_received`; the session reports `reply_saved` and preserves the original terminal stop reason. An Activity event explicitly notes the undelivered reply. This is *not* an uncertain Nomi result: after the API request completes, the operator should reopen the **original ChatGPT conversation**, select it in the dashboard, inspect the checkpoint, and choose **Recover Reply**. For `reply_received` recovery, the bridge sends the *saved* response to GPT without another world POST or Nomi reply request. Do not Reset/Abandon the checkpoint beforehand. A tab reload on the same conversation URL while the API is waiting does not stop the bridge. The change also prevents stopped-session informational logs from hiding the actual navigation failure.

**Resume/reload rules:** Stop/Play after a passive `[wait]` does not create or resend a room checkpoint. A harmless ChatGPT page reload at the same URL outside an active send preserves the room session but deliberately ignores the old GPT response. A reload during a potentially active send remains uncertain. Recovery after a confirmed background world POST but before GPT acknowledgement can safely re-issue the **bridge delivery notice** without re-posting the room event or requesting Nomi's reply, provided private monitoring is active. Uncertain API POST outcomes still require explicit operator approval to prevent duplicates.

The Activity log includes distinct `Nomi API /chat/request attempt` entries; control commands do not produce these entries. The bridge does not change Nomi's private-chat messages.

## Every turn

- Wait for a **complete ChatGPT answer**. A large World Engine action is allowed without a total message-length limit in the bridge.
- Split it **losslessly**, preferably at word/paragraph boundaries, into ordered API room messages of **at most 800 UTF-8 bytes each**. For non-ASCII characters such as emoji, this can be fewer than 800 visible characters. No source text is discarded.
- POST **every chunk in order** to `/rooms/{roomUuid}/chat`. Confirm each submission; track the number of confirmed chunks in session state.
- Only after the **entire ChatGPT turn** is sent, request **one** reply from the selected Nomi using `/rooms/{roomUuid}/chat/request` with her UUID. This follows the uploader API pattern but invokes the Nomi every conversation turn.
- Forward that Nomi reply back into ChatGPT; ChatGPT generates the next turn. Repeat until Stop.

## Reliability and limitations

- **Durable checkpoint per room:** the bridge records `attempt` before each POST, `confirmed` after each acknowledged POST, and `reply_attempt`/`reply_committed` for Nomi responses. Checkpoints live in Edge extension local storage, survive an ordinary browser restart, and are separate from Nomi room history.
- **Read-only API GETs** retry at most eight times for transient errors using 1, 2, 4, 8, 16, 30, 30 second exponential backoff. A content POST, room-creation POST, or ambiguous reply POST is **never** automatically repeated.
- **NoReply / not-ready / rate-limit on a reply request:** continue waiting with exponential backoff (up to 30 seconds between attempts), with no fixed retry count, until Nomi answers or you stop the bridge. The original world message is **not** resent. Some Nomi API calls can themselves remain pending for many seconds, so elapsed time between attempts can exceed the backoff. In build `reply-retry-diagnostics-r9`, the Activity log and copied troubleshooting status include the latest **Nomi API error type, HTTP status, attempt number, and planned retry delay**, so an explicit not-ready response isn't misreported merely as “Nomi is still generating.” These values do not expose your API key.
- **Uncertain content POST:** Stop with its 1-based chunk index and the number of confirmed chunks intact. Review the room/checkpoint, click **Resume or authorize uncertain chunk**, and explicitly accept the risk of duplication. Only the first unconfirmed chunk is retried; earlier confirmed chunks are skipped.
- **Uncertain reply POST:** Review and click **Resume or authorize uncertain reply**. This requests a reply only; it **never** resends the completed world message. A duplicate Nomi reply may result. If a reply was committed before the browser went away, recovery reuses it without requesting another reply.
- **Stop during chunking:** a fully confirmed prefix is retained; use recovery controls rather than starting a new world turn. Abandoning the local checkpoint does not remove content already present in the room.
- **Service-worker restart:** an in-flight POST cannot be inferred to have failed. The checkpoint remains unresolved until recovery is expressly authorized. The bridge requires the original ChatGPT conversation and Nomi room when resuming.
- Only one Nomi may belong to an API room in this mode; rooms containing multiple Nomis are excluded from selection.
- Storage and browser resources remain finite. The bridge imposes no overall length/truncation threshold on World Engine turns, but an exceptionally large output can exceed browser storage limits.
- The older Direct Chat and Group Chat modes retain their existing behavior.
- Existing Direct Chat and browser Group Chat modes are unchanged, including their existing message-size behavior.
- This is an Edge extension mode, not yet wired into the separate portable Windows desktop wrapper.
- Live Nomi account testing is needed. Unit/simulated room tests do not establish real-world API delivery.

## Security

The key is passed only to `https://api.nomi.ai/v1` in an Authorization header, from the extension service worker. It is **not** serialized with the bridge state, shown in the room UI, or copied in troubleshooting data. Use **Clear key** to remove it. Do not commit secrets or exported Chrome/Edge profile data to GitHub.
